## November 4, 2026: the assigned EFA count on both GPU nodes

The health Prolog runs on both GPU nodes and reads the assigned EFA count only from `/etc/aim344-maintenance.json`, which `prepare-target.py` writes on the target alone. On a two-EFA g7e.48xlarge launch the peer therefore expected the G7e profile's four interfaces, failed Check 2 and kept the two-node job from starting. A g7.48xlarge pair is unaffected, because its profile count is two. This change (3579cf27) closes the gap. It is the companion that was installed on the g7.48xlarge pair in Europe (Spain) on November 4, and the participant pass of November 5 ran on it.

What changed:

- `prepare-compute.sh`, which runs on both GPU nodes, takes `AIM344_EXPECTED_EFA_DEVICES` and sets `expected_efa_devices` in `/etc/aim344-maintenance.json`, keeping any other settings in the file. With the variable unset, it writes nothing. On the target, `prepare-target.py` still writes the whole file afterwards, and a rerun of `prepare-compute.sh` with the same count leaves that file byte for byte as it was.
- Step 2 of DEVICE-RECOVERY.md and its section on the G7e count pass the variable to `prepare-compute.sh`.

What the tests cover:

- `tests/test_maintenance.py`: the script's count block and the Prolog's assignment-loading prefix, run against a relocated path. The peer's Prolog reads 2, a target file keeps its other settings, and nothing is written without the variable. Separately, in an `ubuntu:24.04` container run as root at the real path, the Prolog read 2 from the file the block wrote and ignored a caller's 4.
- `tests/test_prepare_target.py`: the generated maintenance configuration is written with `prepare-target.py`'s own writer and loaded through `maintenance.load_config()`. With `suite_entry` removed from the generator, the earlier test passed and this one fails.

## November 3, 2026: allocations without a time limit

Each seat holds its own two nodes for the session, so the participant pages take their allocations without `--time`. Until this change, `job.sh`, `11.device-workload.sh` and the active FLR of `facilitator/device-fault.sh` refused an allocation whose time limit was not 1 to 10 minutes. The tests run on a CPU-only host. One pass on the g7.48xlarge pair has used this change since, and the end of this section says what it reached.

What changed:

- `job.sh`, `11.device-workload.sh` and `facilitator/device-fault.sh` no longer read the allocation's time limit, so an allocation with the partition's default limit, `UNLIMITED` included, is accepted. The other checks stay. The job name starts with `aim344-`, the login profile sets `AIM344_EFA_DEVICE`, the allocation holds two nodes, and the lab controls act only on the one RUNNING job of the seat's participant account on the target.
- The device step of the `efa-reset` incident and of `11.device-workload.sh` has no launcher timeout, and the allocation's limit was its only bound. `common.sh` `run_torch` now gives that step a Slurm step time limit of six minutes (`srun --time=6`). At that limit Slurm sends SIGTERM and, after KillWait, SIGKILL, as it did at the allocation's limit, and the `srun` client and its log stay attached. In the recorded g7.48xlarge runs, the whole device incident ended within 2.5 minutes.
- An allocation without a limit can still be running when its round reaches the deadline. Recovery refuses the round's own RUNNING job and ends no job, so before this change the deadline sweep counted a refused attempt on each pass and stopped after three. The sweep now counts nothing while that job runs. It reports the job, changes nothing, and recovers the node on a later pass after the job ends. A job that is not the round's still counts as an attempt and is refused as before.
- While that job runs, `recover` now refuses with `The faulted allocation is still active. Collect your evidence, end the allocation with exit in the terminal that holds it, then run recover. No job was killed.`
- README.md and DEVICE-RECOVERY.md no longer give `--time` in their `salloc` lines or a 20-minute limit for the DataLoader controls. `13.verify-after-recovery.sbatch` keeps its own `#SBATCH --time=00:25:00`, which bounds that batch job. The lab checks no allocation against it.

The earlier sections below describe the launcher of their date, including its check of the time limit.

## November 3, 2026: a busy controller, and which incident `ended` ends

The end-to-end run of the [previous section's change](#november-3-2026-status-after-an-incident-ends-the-help-lines-and-an-older-lab-record-file) on the g7.48xlarge pair, and two independent reviews of that change, found the problems this change fixes. The tests run on a CPU-only host. Two passes on the g7.48xlarge pair have used this change since, the second at the [next section's change](#november-3-2026-allocations-without-a-time-limit), and the end of this section says what they reached.

What changed:

- The controller takes one request per seat at a time. In the end-to-end run, a `status` in terminal B arrived at the moment the device incident's launcher asked `next` after progress. The controller refused that request with `Another request for this assignment is in progress. Wait for it to finish, then run status.`, the launcher treated the refusal as final, and the job ran 120 seconds with no fault. The controller gives that reply before it does anything, so `job.sh` now sends such a request again, once a second for up to 30 seconds, and counts only the other replies as attempts. It does the same for the first `next` of `job.sh incident` and for `ended`. Any other refusal is still final.
- `ended` takes the incident's issue id, which the profile now carries as `issue_id`, and the controller records the end of that incident only. Before, the controller ended the incident issued last, so an `ended` that arrived after a second terminal had issued the next incident ended that one.
- A `dataloader` rerun with `--dataset-cache worker-thread` or `--reinit-in-worker` whose job completes sends `ended`, because the incident's page ends it with one of these fix runs. In the end-to-end run, `status` after those runs still said that Incident 3 was under way. A rerun without either option, or one whose job fails, sends nothing.
- For the device incident, `ended` gives the same exit status and reply as for a job incident and records nothing, so its reply no longer tells the two kinds apart. The incident still ends with `recover`.
- The controller refuses `ended` for an incident whose profile was never handed over, with `Incident <n> has not started yet; follow your page.`, and an issue id it never issued with `No incident with that issue id has been issued on your seat.`
- `--operator status` prints `ended <time>` after the issue time of each job incident that has ended.

The controller and `12.device-exercise.sh` have to be reinstalled with the launcher: the earlier controller refuses `ended` with an argument, and the earlier launcher sends it without one.

What the tests cover:

- `tests/test_quiz_controls.py`: the `ended <issue id>` grammar, a late `ended` for Incident 1 after Incident 2 was issued, an unknown issue id, an incident whose profile write failed, the device incident's reply compared with a job incident's, and the operator view's end time.
- `tests/test_job_launcher.py`: busy replies to `ended`, to the first `next` and to the controller step's `next`, the 30-second bound, a refusal from another table that is not sent again, the issue id that `ended` carries, a profile without a valid issue id, the four completing fix reruns, and the reruns that do not end the incident. The `efa-reset` resume test now checks that no request of any verb is sent.

Measured on hardware, in the first pass, which ran pages 020 and 030 and Incidents 1 to 5 on the g7.48xlarge pair at this change:

- Right after Incident 3's fix run, `status` printed `Next: Incident 3 has ended. Start the next incident the way your page shows.`
- While the device incident's launcher held the controller for its `next`, about 6 s, 15 of 28 `status` calls in terminal B got the busy reply with exit 3, and the next call printed the fault phase. The launcher's own request got no busy reply, and the fault was applied once. Since the [change to the ubuntu account](#november-4-2026-the-lab-controls-as-the-clusters-ubuntu-account), `status` takes no lock and gets no busy reply.

The second pass ran the pages' Incidents 1, 3 and 5 in a three-entry schedule, which issued Incident 3 as incident 2. Right after Incident 3's fix run, `status` printed `Next: Incident 2 has ended. Start the next incident the way your page shows.`

Still to measure on hardware:

- A busy reply to one of `job.sh`'s requests, which the launcher sends again. Neither pass reached it, and neither did a separate check with three parallel `status` loops around Incident 1's `next` and `ended`.

## November 3, 2026: status after an incident ends, the help lines and an older lab-record file

The end-to-end run of the [previous section's change](#november-3-2026-status-before-the-device-fault-the-kernel-window-collection-and-cleanup-failures) on the g7.48xlarge pair, and an independent review of that change, found the problems this change fixes. No hardware run has used it yet. The tests run on a CPU-only host.

What changed:

- `job.sh resume` sends `ended` to the lab controls once its job has completed, and the controller records that the current incident has ended. `status` then reads `Next: Incident <n> has ended. Start the next incident the way your page shows.` until the next incident is issued, or `Next: Incident <n> has ended. It was the last incident for this seat.` after the seat's last one. In the g7.48xlarge run, `status` after the resume of each job incident still said that the incident was under way. A resume whose job fails sends nothing. ## November 3, 2026: the replica check after an aborted collective, the NCCL protocol on g7.48xlarge, and both images in the page cache

The end-to-end run on the two g7.48xlarge nodes in Europe (Spain), at the revision before the [review of the integrated code](#november-3-2026-the-review-of-the-integrated-code), and the measurements that followed it found three problems. This change fixes them. No hardware run has used it yet. The tests run on a CPU-only host.

What the g7.48xlarge runs found:

- In the device incident, 13 ranks on both nodes each printed a replica check line naming its own GPU, at the same step, a minute or more after the EFA reset. These lines did not compare that step's checksums. The step's all-gather could not complete after the reset. The read of its output waited until the NCCL watchdog aborted the communicator (torchrun sets `TORCH_NCCL_ASYNC_ERROR_HANDLING=1`), and then returned the buffer as the abort left it: the rank's own new checksum among the previous step's values.
- Under `OFI_NCCL_PROTOCOL=RDMA`, NCCL ran every all-reduce from 64 KiB to 8 MiB as LL, and Check 5's 1 to 8 MiB rows ran at 0.25 to 0.30 GB/s of bus bandwidth in the verification job (1 MiB 6,593 µs, 8 MiB 63,978 µs). With `NCCL_PROTO=Simple` added, the same job ran these rows at 4.06 to 13.91 GB/s (1 MiB 484.57 µs, 8 MiB 1,131 µs). 16 MiB stayed at 31.26 GB/s (31.21 without Simple) and 128 MiB at 39.61 GB/s (39.58), and the job under Simple passed with `#wrong` 0 in both columns. Sizes up to 512 KiB took longer under Simple, for example 103.07 µs against 54.13 µs at 8 B. The 2 GiB all-reduce of the sweep reached 39.85 GB/s under Simple and 39.88 GB/s without it in the same allocation. The SENDRECV verification job, where the plugin itself adds `NCCL_PROTO=simple`, ran 1 MiB at 3.40 GB/s, 16 MiB at 7.64 GB/s and 64 MiB at 9.06 GB/s. That job had NCCL's TUNING log on, which interleaves with the table, so the suite rejected its table, and its rows were rebuilt from the raw log with `#wrong` 0. `NCCL_PROTO=^LL` is not the fix: an exclusion list makes NCCL enable LL128 without its NVLink check, and on this PCIe-only instance it ran LL128 up to 64 MiB, with 16 to 64 MiB at 2.80 to 4.21 GB/s. NCCL's documentation warns that LL128 on a platform that does not support it can corrupt data.
- The first torch container on a node took 168 s to create when the node had not read the image since its reboot, against about 5 s with the image in the page cache. The launcher's 180 s limit ended that healthy job before its first progress line. The first NCCL container on the same node took 103 s. Supported recovery hashes both images on the target, which leaves them cached, but nothing reads them on the other node or after a reboot outside recovery.

What changed:

- The replica check compares only after an all-gather that completed. When this rank's NCCL process group has recorded a failed or timed-out collective (`get_error()`), the step prints neither the differing line nor the "agrees again" line and does not count the step, and rank 0 prints no window report. The watchdog records the error before it aborts, and only the abort releases the read of an unfinished all-gather, so the check always sees the error after such a read. Incident 4's flip records no NCCL error, and its lines are unchanged.
- On g7, `apply_g7_protocol` exports `NCCL_PROTO=Simple` with `OFI_NCCL_PROTOCOL=RDMA`, for every torch job and sweep, and prints both on its `host=` line. Check 5 does not run that detection, so the site manifest's `verification_environment` accepts `NCCL_PROTO`, and `run_check5` passes it into the container with the other NCCL and MPI settings. A g7.48xlarge manifest sets it to `Simple` ([Check 5 protocol on G7](facilitator/DEVICE-RECOVERY.md#check-5-protocol-on-g7)). This is the companion's interim setting, while a separate investigation establishes whether aws-ofi-nccl needs a fix for LL on this instance type. The `g7.*` pattern of `apply_g7_protocol` matches g7.48xlarge and g7.24xlarge and does not match g7e. Simple was measured on g7.48xlarge only.
- `facilitator/image-cache.py read` reads both images once, and `check` reports each image's resident pages with `mincore` and reads no data. Both exit 1 unless every page of both images is in the page cache. `prepare-compute.sh` reads both images at its end. [Images in the page cache](facilitator/DEVICE-RECOVERY.md#images-in-the-page-cache) says when to read them and adds the check to the pre-session checks.

What the tests cover:
